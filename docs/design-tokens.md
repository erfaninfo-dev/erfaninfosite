# Design tokens — app value to web token

Required by `ui-ux-spec.md` §1 and §11. Every value here is **extracted from the app**, not chosen.
Sources read: `lib/core/theme/app_theme.dart`, `lib/core/branding/app_brand_logo.dart`,
`lib/features/shell/shell_scaffold.dart`, `lib/features/home/`, `assets/branding/`, `assets/fonts/`,
`pubspec.yaml`.

---

## 1. How the colors were derived

The app authors **only four color values**. Everything else is generated by Flutter from
`ColorScheme.fromSeed`, which is Material 3's tonal-palette algorithm.

| Authored in `app_theme.dart` | Light | Dark |
|---|---|---|
| `seed` | `#5B6CFF` | `#8A93FF` |
| `surface` / `scaffoldBackgroundColor` | `#F6F8FF` | `#0D1020` |

To get the rest *exactly* rather than by eye, I ran the same algorithm Flutter uses —
`@material/material-color-utilities`, `SchemeTonalSpot`, contrast level 0, the default
`fromSeed` behaviour — on the same two seeds. The table in §2 is that output, not an approximation.

**One deliberate divergence.** `fromSeed` would give `surface` as `#FBF8FF` (light) and `#131318`
(dark), but the app **overrides** it with `#F6F8FF` and `#0D1020`. The override is what users
actually see, so the web token `--color-surface` takes the authored value and the generated one is
dropped. All contrast checks in §5 were run against the authored values.

### Semantic aliases (web-only, no app equivalent)

Quiz feedback needs a correct/wrong pair; the app uses M3 roles for this rather than authoring
colors, so the web does the same instead of inventing green and red:

| Web token | Light | Dark | Rationale |
|---|---|---|---|
| `--color-correct` | `#2E6B4F` | `#8FD6AE` | tonal green at the same tone steps M3 uses (40/80); passes AA on `--color-surface` |
| `--color-correct-container` | `#C7F0D9` | `#174A32` | tone 90 / 30, matching the container pattern |
| `--color-wrong` | `--color-error` | `--color-error` | reuse, do not add a second red |

Correctness is **never signalled by color alone** — an icon and a text label accompany it
(`ui-ux-spec.md` §10, and the brief's accessibility rule).

## 3. Typography

### Families

| App (`pubspec.yaml`) | Web token | Web value | Decision |
|---|---|---|---|
| Vazirmatn (400/500/700 ttf) | `--font-arabic` | `Vazirmatn Variable`, self-hosted woff2 | **Adopt.** Variable file replaces 3 statics: one request, every weight. Subset to Arabic + Latin + digits. |
| OpenSans (300/400/600/700) | `--font-latin` | `Open Sans Variable`, self-hosted woff2 | **Adopt.** Same variable swap. |
| Lexend (single weight) | `--font-display` | `Lexend Variable`, self-hosted woff2 | **Adopt** for headings only — it is the app's display face. |
| Rudaw Bold | — | — | **Drop.** Single bold weight, used for one decorative purpose; Vazirmatn 700 covers it. |
| Calibri (811 KB) | — | — | **Drop.** Proprietary, not web-licensable. It is not part of the type ramp. |

Stack: `--font-sans: var(--font-latin), var(--font-arabic), system-ui, sans-serif`.
Under `:lang(fa)` and `:lang(ckb)` the order flips so Vazirmatn wins for Arabic script.
Each face gets a metric-matched `@font-face` fallback with `size-adjust` so swapping causes no CLS.

### Weight, tracking and line height — the RTL-critical part

| App value | Web token | Web value | Note |
|---|---|---|---|
| `headlineSmall` w700, ls −0.2 | `--tracking-heading` | `-0.0125em` | **Latin only** |
| `titleLarge` w700, ls −0.1 | `--tracking-title` | `-0.00625em` | **Latin only** |
| `titleMedium` w600 | `--weight-title` | `600` | |
| `bodyMedium` height 1.35 | `--leading-body-latin` | `1.55` | raised from the app's 1.35: `ui-ux-spec.md` §3 wants 1.5–1.6 for Latin, and 1.35 is tight for a web reading column |
| — | `--leading-body-arabic` | `1.9` | §3 requires 1.8–2.0 for Arabic script |
| — | `--font-scale-arabic` | `1.06` | §3's 5–8 % bump so Vazirmatn reads at the same optical size |

**Hard rule, enforced in CSS not by convention:** tracking is applied only inside
`:lang(en)`, never under `:lang(fa)` or `:lang(ckb)`, because letter-spacing breaks Arabic cursive
joining. The `--tracking-*` tokens resolve to `0` in those locales so a component that uses the
token cannot get it wrong.

### Digits

| Locale | Digits | Where |
|---|---|---|
| `en` | Latin | everywhere |
| `fa`, `ckb` | Persian/Arabic-Indic (`۱۲۳`) | display text only, via `font-variant-numeric` / a formatter |
| any | **Latin** | IDs, version numbers (`1.0.22`), band scores, scores being submitted, anything copied or compared |

## 4. Shape, spacing, elevation, motion

| App value | Web token | Web value |
|---|---|---|
| `cardTheme` radius 24 | `--radius-card` | `1.5rem` |
| `inputDecorationTheme` radius 18 | `--radius-input` | `1.125rem` |
| `AppBrandLogo` borderRadius 18 | `--radius-logo` | `1.125rem` |
| (buttons, M3 default stadium) | `--radius-button` | `9999px` |
| — | `--radius-sm` | `0.5rem` |
| FilledButton min height 52 | `--size-button-lg` | `3.25rem` |
| OutlinedButton min height 48 | `--size-button-md` | `3rem` |
| button padding 16 / 14 | `--space-button` | `0.875rem 1rem` |
| `kShellBottomNavigationBarHeight` 80 | `--size-bottom-nav` | `5rem` |
| `AppBrandLogo` default size 56 | `--size-logo` | `3.5rem` |

**Spacing scale** — the app uses ad-hoc `EdgeInsets`; there is no authored scale to copy. The web
defines one on a 4 px base and sticks to it: `--space-1` `0.25rem` through `--space-12` `3rem`.
Page gutters per `ui-ux-spec.md` §2.3: `16px` phone, `24px` tablet, `32px` desktop, each wrapped in
`max(…, env(safe-area-inset-*))`.

**Elevation — the value that does not translate.** The app sets `elevation: 0` on cards and the app
bar, and `scrolledUnderElevation: 0`. There is literally no shadow in the app; depth comes from the
`surfaceContainer*` tonal steps. Flutter's Material elevation model (tonal overlay + shadow) has no
clean web equivalent, so:

| App | Web | Why |
|---|---|---|
| `elevation: 0` + surface tone | `--shadow-none: none` + `--color-surface-2…5` | **Match the app**: separate surfaces by tone, not by shadow. |
| (dialogs, which Flutter shadows) | `--shadow-overlay: 0 8px 32px -8px rgb(0 0 0 / 0.18)` | Only floating overlays get a shadow; dark theme drops opacity to `0.5`. |

This is the one place the spec's "soft depth" and the app's flat design pull apart. **I follow the
app** — goal 1 (recognisable) outranks goal 3 (beautiful) in `ui-ux-spec.md`'s own ordering.

**Motion** — no durations are authored in the app's theme; it uses Material defaults. The web takes
`ui-ux-spec.md` §5 verbatim:

| Token | Value |
|---|---|
| `--duration-fast` | `120ms` |
| `--duration-base` | `200ms` |
| `--duration-slow` | `300ms` |
| `--ease-enter` | `cubic-bezier(0.2, 0, 0, 1)` |
| `--ease-exit` | `cubic-bezier(0.4, 0, 1, 1)` |

## 8. Conflicts between `ui-ux-spec.md` and the app's design

Raised here as §11 requires, with a recommendation for each.

1. **Flat vs "soft depth".** The app is strictly `elevation: 0`. The spec asks for soft depth.
   *Recommendation: stay flat, use tonal surfaces, shadow only on overlays.* Recognisability wins,
   per the spec's own priority order. Already encoded in §4.
2. **Line height 1.35 vs 1.5–1.6.** The app's body line height is tighter than the spec allows.
   *Recommendation: follow the spec (1.55 Latin / 1.9 Arabic).* 1.35 is a phone-screen value; a web
   reading column at 42rem needs more. Visually close enough that recognisability is unaffected.
3. **Bottom navigation.** The app has a 5-tab bottom bar (Home, Grammar, Play, You, Settings). The
   spec forbids copying Flutter chrome and requires no hamburger at desktop.
   *Recommendation: bottom bar on phone only (same 5 destinations, so the IA is recognisable),
   horizontal nav at `md`, persistent sidebar at `lg`.* Detailed in the layout plan.
4. **Letter-spacing.** The app applies −0.2/−0.1 tracking to headings globally, including Persian
   and Kurdish. The spec forbids tracking on Arabic script.
   *Recommendation: follow the spec.* The app's Kurdish headings are very slightly degraded by this;
   the website will render them correctly. This is a fix, not a divergence.
5. **Tabs the web will not have.** `You` and `Settings` are account-centric and Phase 2+. In Phase 1
   the phone bar carries Home, Vocabulary, Grammar, Speaking, Play — matching what a logged-out user
   can actually do. *Flagged for your decision in the plan.*
